# 项目复盘与学习收获

## 最难的问题

对我而言，最难的部分是把题面中的“合理重规划”转成具体、可计算的业务行为。开始讨论时，任务计划与最终方案、参考素材与生成脚本、工具报价与已发生费用的边界还不够明确。如果这些概念没有先理清，后面很容易得到一个能串行调用工具、却无法解释为什么调整计划的程序。

我通过反复核对题目和完整业务流程，明确了输入、工具和成果之间的关系，并发现固定单次生成费会限制调整空间。因此，我提出让生成成本随选用素材数量变化，同时保持素材仅为参考资料。这个决定使“选择哪些素材”成为模型真正需要做的业务判断，也让调整前后的效果可以用同一套公式验证。

另一个难点是动态调整之后，账仍然要算对。估算本身耗时，失败调用也消耗额度，保存还要预留时间。最终实现使用“已发生消耗＋尚未完成步骤＋保存”计算预计总量，并在执行前再次检查。成功结果保留，原有消耗不清零，使重规划与失败续跑能够使用一致的约束。

## 学习收获

### 先把业务问题说清楚 再确定实现方式

这次让我更明确地认识到，字段和工具定义会直接影响 Agent 能作出哪些决策。先设计一套能手算的费用、时间和小规模数据，就能讨论什么行为合理、什么结果算成功，并为后续自检提供依据。

我也认识到，控制范围本身是重要的工程判断。对这道题，素材重复度分析、真实模型账单计算等内容并不直接服务验收。我主动将这些方向排除，让核心链路和异常处理优先完成。

### 模型判断与程序约束需要各自明确

模型负责结合主题选择素材，并根据工具反馈决定调整、重试或停止；程序负责准确计算费用、校验依赖、限制执行次数和确认保存结果。这种分工让动态决策有空间，也让硬性约束有可靠的执行依据。

状态也需要分层理解：成本估算工具执行成功，可以同时得到“方案不可行”的结果；脚本生成成功，也不代表最终方案保存成功。分别记录这些状态，才能解释失败发生在哪里，以及哪些结果可以继续使用。

### 验收需要能回到实际输入和执行记录

我要求在完成实现后增加独立子 Agent 验收，并再次核对交付规范。关注点是结果能否被复现：预算是否算对、失败有没有被错误记为成功、重复请求有没有新增保存、续跑是否重做成功步骤。

项目的真实运行还说明，程序化断言有明确边界。首轮输出虽然通过结构与引用检查，仍出现了缺少依据的宣传表述；AI 助手通过内容复核发现问题、修改提示词并重跑。后续评价生成效果时，应同时查看自动检查结果和实际内容，不只看汇总中的通过数量。

## 下一步

1. **完成交付复现。** 在自己的终端复现正常完成、超限重规划和失败续跑三条关键路径，对照输入、工具返回和累计消耗，逐步解释为什么继续、调整或停止；同时核对 GitHub 文件与最终提交 SHA。
2. **用少量新输入检验稳定性。** 在现有验收点内改变主题表达、预算和时间组合，优先观察临界额度及失败后剩余额度不足的情况，确认行为不只适用于现有固定样例。
3. **让后续修改有前后对照。** 修改提示词或检索匹配方式时，沿用同一组输入比较任务状态、选材、费用和生成内容，保留改进与退化的记录，再决定是否采用修改。

后续仍以题目验收和结果可解释为优先，不增加没有明确需求的功能。
